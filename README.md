## 🎯 핵심 성과: [Phase2] 게시판 목록 조회 API 성능 최적화

### 📌 Why: 무엇을 해결하고 싶었나요?

게시판의 핵심 기능인 '게시글 목록 조회' 기능 구현 후, 쿼리 로그를 분석하는 과정에서 숨겨진 성능 병목을 발견했습니다. 게시글을 조회하는 1개의 쿼리 이후, 각 게시글에 연결된 댓글이나 작성자 정보를 가져오기 위해 **게시글의 수(N)만큼 추가 쿼리가 발생하는 N+1 문제**였습니다.

이는 데이터가 수백, 수천 건으로 증가할수록 서버에 심각한 부하를 주어 **서비스 전체를 마비시킬 수 있는 잠재적인 장애 포인트**였습니다.

---

### 🛠️ What: 그래서 무엇을 만들었나요?

N+1 문제를 해결하기 위해 **Fetch Join**을 적용하여 연관된 엔티티를 단 한 번의 쿼리로 함께 조회하도록 JPQL을 개선했습니다. 

나아가, Fetch Join의 잠재적 단점을 보완할 더 나은 대안을 탐구하기 위해 **세미 조인(Semi-Join)과 스트림 API를 조합하는 방식**과 기존 방식의 성능을 **객관적인 데이터로 비교하는 테스트 환경**을 설계했습니다.

---

### 🔍 How: 이 목표를 어떻게 해결했나요?

#### 1. 문제 발견 및 Fetch Join을 통한 1차 해결

- `@SpringBootTest` 환경에서 API를 테스트하며 실행되는 쿼리 로그를 통해 N+1 문제를 명확히 인지했습니다.
- 가장 널리 알려진 해결책인 **Fetch Join**을 적용하여 즉시 로딩이 필요한 연관 관계의 엔티티를 함께 조회하도록 Repository 코드를 수정하여 1차적으로 문제를 해결했습니다.

#### 2. 이론에 기반한 심화 탐구 및 대안 가설 수립

Fetch Join이 야기할 수 있는 문제점을 학습했습니다:

- **카테시안 곱(Cartesian Product)**: 1:N 관계에서 게시글이 답변 개수만큼 중복 전송되어 네트워크 비용 증가
- **페이징 한계**: DB가 아닌 메모리에서 페이징이 처리되어 `setMaxResults`가 의도대로 작동하지 않음

이때, 기초 데이터베이스 이론을 공부하며 배웠던 세미 조인(Semi-Join)이 조인 연산의 비용을 크게 줄여준다는 사실을 떠올렸습니다.

**세미 조인의 핵심 원리**: 조인에 필요한 최소한의 키(ID) 정보만 먼저 추출하여 데이터 전송량을 줄이는 관계 대수 연산

이 이론적 지식을 바탕으로, **필요한 ID 목록만 먼저 조회하고(세미 조인 원리 응용), 조회된 독립적인 데이터들을 애플리케이션단에서 스트림 API로 조합하면 Fetch Join보다 효율적일 수 있다**는 새로운 가설을 수립했습니다.

**스트림 API를 선택한 이유:**

- **DB 레벨 최적화의 한계 보완**: 세미 조인 전략으로 3개의 독립적인 쿼리 결과를 받아오면, 이를 조합하는 과정이 필수적으로 필요합니다.
- **O(n) 시간 복잡도 보장**: `Collectors.toMap()`으로 답변 개수를 Map 구조로 변환하여 O(1) 조회가 가능하게 만들고, `stream().map()`으로 최종 DTO를 조립합니다. 전통적인 이중 반복문 방식은 O(n²)의 복잡도를 가지지만, 스트림 API와 Map을 활용하면 O(n)으로 개선됩니다.
- **선언적 코드**: 함수형 프로그래밍 패러다임을 통해 "무엇을 할 것인가"에 집중하여 코드 가독성과 유지보수성을 높였습니다.

#### 3. 객관적 검증을 위한 테스트 설계

두 방식의 성능을 정확히 비교하기 위해, 실제 프로덕션 환경을 시뮬레이션하는 테스트 인프라를 구축했습니다:

- Local MySQL 8.0 환경 구성 (Docker 대신 로컬 인스턴스 사용으로 I/O 오버헤드 제거)
- **10,000개 게시글, 100,000개 답변**의 대용량 더미 데이터 생성 (게시글당 평균 5~20개 답변)
- **Hibernate Statistics API**를 활용한 정밀한 성능 지표 수집 (쿼리 수, 엔티티 로드 수, 실행 시간)

### 💡 데이터 규모별 성능 분석

#### 핵심 인사이트

| 데이터셋 | Semi Join | Fetch Join | 성능 개선율 | Entity Load 비율 |
|---------|-----------|------------|------------|------------------|
| 1,000건 | 20ms | 683ms | 97.1% | 40 vs 14,277 (357배) |
| 5,000건 | 16ms | 1,430ms | 98.9% | 40 vs 68,125 (1,703배) |
| 10,000건 | 70ms | 6,506ms | 98.9% | 40 vs 136,518 (3,413배) |

**1. 스케일 효율성**
- Semi Join은 데이터 증가에도 안정적 성능 유지 (16-70ms)
- **이유**: 페이지네이션(20개 제한)으로 항상 동일한 엔티티(40개)만 로드

**2. Cartesian Product의 재앙**
- Fetch Join은 데이터가 10배 증가할 때 성능이 9.5배 악화 (683ms → 6,506ms)
- **이유**: 질문당 평균 10개 답변 → 10배 중복 전송 (14,277개 → 136,518개)

**3. 답변 수와의 상관관계**
- 답변이 많을수록 (평균 5-20개) Fetch Join의 Cartesian Product 문제가 극대화되어 Semi Join의 성능 우위가 더욱 명확해졌습니다.

**4. 예외 시나리오**
- 답변이 1-2개로 매우 적은 경우, Fetch Join의 단일 쿼리 장점(네트워크 왕복 1회)이 Semi Join의 3회 쿼리 비용을 상쇄할 수 있습니다 (추가 검증 필요)

### 📖 실무 적용 가이드 (When to Use Which)

각 쿼리 전략의 Trade-off를 기반으로 한 실무 의사결정 기준:

| 상황 | 권장 방식 | 이유 |
|------|----------|------|
| 1:N 관계에서 N이 많은 경우<br>(평균 5개 이상) | **Semi Join** | Cartesian Product 방지로<br>네트워크 비용 최소화 |
| 페이징이 필수인 API<br>(게시판, 목록 조회) | **Semi Join** | DB 레벨에서 정확한 페이징 보장 |
| N이 매우 적은 경우<br>(평균 1-2개) | **Fetch Join 고려** | 단일 쿼리로 네트워크 왕복 감소<br>(단, 검증 필요) |
| 프로덕션 환경 | **Lazy Loading 금지** | N+1 문제로 서비스 마비 위험 |

#### 의사결정 프로세스

1. 평균 연관 엔티티 수 확인 (5개 이상 → Semi Join)
2. 페이징 요구사항 확인 (필수 → Semi Join)
3. 성능 테스트로 최종 검증 (본 프로젝트처럼 Hibernate Statistics 활용)

## 🎤 Q&A

### Q: "Fetch Join이 더 나은 경우도 있지 않나요?"

**A**: 네, 1:N 관계에서 N이 1-2개로 매우 적을 때는 Fetch Join의 단일 쿼리 장점이 있을 수 있습니다. 하지만 본 테스트의 게시판 시나리오(평균 10개 답변)에서는 Cartesian Product 비용이 압도적이어서 Semi Join이 97-99% 빠릅니다.

### Q: "3개 쿼리 vs 1개 쿼리, 네트워크 레이턴시는?"

**A**: 로컬 MySQL 환경에서는 레이턴시가 1ms 미만이지만, 실제 프로덕션(원격 DB)에서 3회 왕복 비용(~15ms)이 발생합니다. 그러나 Fetch Join의 Cartesian Product로 인한 데이터 전송량(136,518 vs 40 엔티티)이 훨씬 큰 병목입니다. 테스트 결과(Semi 70ms vs Fetch 6,506ms)가 이를 증명합니다.

### Q: "왜 1K, 5K, 10K를 선택했나요?"

**A**: 스케일 증가에 따른 성능 추세를 관찰하기 위함입니다. 실제로 1K→10K(10배 증가) 시 Fetch Join은 9.5배 느려졌지만, Semi Join은 페이지네이션으로 3.5배만 느려져 스케일 효율성을 입증했습니다.

## 🎯 핵심 성과: [Phase 3] 100 VU 동시 트래픽 환경에서 가설 검증

### 📌 Why: 단일 사용자 최적화가 동시 트래픽에서도 유효한가?

Phase 2에서 단일 사용자 기준의 조회 성능을 개선했지만, 실제 서비스에서는 다수 사용자가 동시에 요청합니다.

이에 "단일 사용자 환경에서 빠른 쿼리가 100 VU 동시 접속 환경에서도 안정적으로 동작하는가?"를 검증하고자 k6 기반 부하 테스트 환경을 구축했습니다.

검색 API에는 Covering Index와 FULLTEXT(ngram) 인덱스를 적용하고, 요청마다 수행되던 실시간 랭킹 집계는 Spring Scheduled 배치로 분리했습니다. Prometheus와 Grafana를 추가해 커넥션 풀과 응답 시간을 관측할 수 있도록 구성했습니다.

### 🔍 Phase 3에서 얻은 결과와 가설

100 VU 부하 테스트 결과 검색 API는 기존 LIKE 풀스캔 대비 다음과 같이 개선되었습니다.

| 지표 | Before | Phase 3 |
|---|---:|---:|
| P95 응답 시간 | 24.04s | 2.18s |
| TPS | 4.42 req/s | 37.3 req/s |
| 문제 요청 비율 | 79.88% | 51.58% |

그러나 약 51%의 요청이 여전히 실패하거나 기준을 충족하지 못했습니다.

당시에는 인덱스 최적화 이후에도 문제가 남았다는 점에서 **HikariCP 커넥션 풀 포화가 다음 병목일 것**이라고 가설을 세웠습니다.

이를 검증하기 위해 커넥션 풀 크기를 20 → 40 → 80으로 변경했지만 문제 비율은 50~52%에서 거의 변하지 않았습니다.

→ **HikariCP 병목 가설은 반증되었습니다.**

이 시점부터 "인프라의 문제가 아니라, 우리가 놓친 SQL 실행 구조가 있는 것은 아닌가?"라는 방향으로 원인을 다시 탐색했습니다.

## 🎯 핵심 성과: [Phase 4] 가설 반증 후 SQL 실행계획 기반 병목 재탐색

### 1. 애플리케이션 로그에서 숨겨진 오류 발견

Phase 3의 51.58%는 단순한 느린 응답 비율이 아니었습니다.

FULLTEXT용 Native Query에 이미 `ORDER BY q.CREATE_DATE DESC`가 존재했지만, Pageable의 `Sort(createDate)`가 추가로 붙으면서 다음과 같은 SQL 문법 오류가 발생하고 있었습니다.

`ORDER BY q.CREATE_DATE DESC, q.createDate desc`

키워드 검색 요청 비중이 약 50%였기 때문에, 해당 요청들이 즉시 500 에러로 실패하면서 실제 DB 부하의 절반이 발생하지 않고 있었습니다.

즉, Phase 3에서 관측된 P95 2.18s와 TPS 37.3 req/s는 실제 전체 검색 부하가 적용된 상태의 최종 성능으로 볼 수 없었습니다.

### 2. 오류 수정 후 진짜 DB 병목 노출

Native Query의 Sort 중복 문제를 수정한 뒤 다시 부하 테스트를 수행하자 오히려 P95가 크게 증가했습니다.

그동안 즉시 실패하던 요청까지 실제 검색을 수행하면서 숨겨져 있던 DB 부하가 처음으로 드러난 것입니다.

`performance_schema`를 분석한 결과 count 쿼리가 전체 DB 시간의 대부분을 소비하고 있었고, 평균 수십만 행을 검사하고 있었습니다.

### 3. EXPLAIN 분석 — OR 조건이 FULLTEXT 인덱스를 무력화

검색 조건은 다음과 같이 FULLTEXT와 LIKE 조건이 OR로 연결되어 있었습니다.

`MATCH(...) AGAINST (...) OR username LIKE '%keyword%'`

OR 조건 중 하나가 인덱스를 사용할 수 없자 MySQL 옵티마이저는 같은 조건에 포함된 FULLTEXT 인덱스까지 사용하지 않았습니다.

EXPLAIN 결과:

- QUESTION 접근 방식: `ALL`
- 스캔 행 수: 9,925
- `possible_keys = NULL`
- FULLTEXT 인덱스 미사용

즉, Phase 3에서 Covering Index와 FULLTEXT Index를 생성했지만 **인덱스가 존재한다는 사실과 실제 실행계획에서 선택된다는 사실은 별개의 문제**였습니다.

### 4. OR → UNION + IN: 인덱스 사용은 개선됐지만 반복 실행 문제 잔존

OR 조건을 각 검색 조건별 UNION으로 분리해 각 조건이 자신의 인덱스를 사용할 수 있도록 변경했습니다.

그 결과 QUESTION 테이블은 Covering Index를 이용해 10행만 읽게 되었습니다.

하지만 UNION 결과를 `IN` 서브쿼리로 받으면서 EXPLAIN에 `DEPENDENT SUBQUERY`와 `DEPENDENT UNION`이 남았습니다.

즉, 바깥 행마다 서브쿼리가 반복 실행되는 구조가 남아 있었습니다.

### 5. UNION + INNER JOIN: 최종 SQL 튜닝

최종적으로 `IN` 서브쿼리를 JOIN으로 변경했습니다.

그 결과:

- `DEPENDENT SUBQUERY` 제거
- `DERIVED + eq_ref` 구조로 변경
- QUESTION: `idx_question_covering` 사용
- QUESTION 스캔: 9,925행 → 10행
- 검색 파생 테이블: `ft_idx_question_search` FULLTEXT 인덱스 실제 적중
- 서브쿼리 반복 실행 제거

또한 원본 OR / UNION + IN / UNION + JOIN 세 쿼리 모두 검색 결과가 1,475건으로 동일한 것을 검증해, 성능 개선 과정에서 검색 결과의 정합성이 변하지 않았음을 확인했습니다.

### 🏆 결론 및 배운 점

1. **성장의 궤적**  
   [Phase 1]의 기능 구현에서 시작해, [Phase 2]의 단일 사용자 쿼리 튜닝, [Phase 3]의 100 VU 부하 테스트와 가설 검증, [Phase 4]의 실행계획 기반 병목 재탐색까지 단계적으로 확장했습니다. 단순히 빠른 쿼리를 만드는 것을 넘어, 실제 동시 트래픽 환경에서 병목을 관측하고 검증하는 경험으로 발전시켰습니다.

2. **가설을 고집하지 않고 데이터로 반증하는 과정**  
   Phase 3에서는 남은 병목의 원인을 HikariCP 커넥션 풀 포화로 가정했지만, 풀 크기를 변경한 실험에서도 지표가 개선되지 않아 가설을 반증했습니다. 이후 애플리케이션 로그 → `performance_schema` → `EXPLAIN` 순으로 관측 범위를 좁혀 실제 원인을 다시 추적했습니다.

3. **인덱스 생성과 실제 인덱스 활용은 다른 문제**  
   Covering Index와 FULLTEXT(ngram) 인덱스를 생성했더라도 SQL 구조에 따라 옵티마이저가 이를 사용하지 않을 수 있음을 확인했습니다. `OR` 조건으로 FULLTEXT 인덱스가 무력화되는 문제를 발견했고, `UNION + IN`에서도 `DEPENDENT SUBQUERY`에 의한 반복 실행이 남아 있음을 실행계획으로 검증했습니다. 최종적으로 `UNION + INNER JOIN` 구조로 재설계해 Covering Index와 FULLTEXT 인덱스가 실제 실행계획에서 사용되도록 개선했습니다.

4. **성능 개선은 수치뿐 아니라 결과의 정합성까지 검증해야 함**  
   원본 OR 쿼리, `UNION + IN`, `UNION + INNER JOIN`의 검색 결과가 모두 1,475건으로 동일한지 확인해 SQL 구조 변경 이후에도 기능적 정합성이 유지되는 것을 검증했습니다. 이후 100 VU 부하 테스트를 다시 수행해 HTTP 실패율 0.00%, 3초 SLO 초과율 0.44%까지 확인했습니다.

5. **트레이드오프를 고려한 시스템 설계**  
   모든 연산을 실시간 요청 경로에서 처리하기보다, 랭킹 집계처럼 즉시성이 상대적으로 낮은 작업은 배치로 분리했습니다. 이를 통해 실시간성(Real-time)과 안정성(Stability) 사이의 트레이드오프를 요구사항에 따라 판단하는 경험을 얻었습니다.

6. **지표는 시나리오와 SLO 단위로 관리해야 함**  
   서로 다른 엔드포인트나 테스트 시나리오의 지표를 하나의 성과로 합치면 기술적으로 잘못된 해석이 될 수 있음을 확인했습니다. 이후 각 시나리오의 SLO, P95, TPS, 실패율을 분리해 기록하고, 동일한 조건에서 재측정한 결과만 성과 지표로 사용하도록 기준을 정립했습니다.
