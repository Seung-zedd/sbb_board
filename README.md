## 🎯 핵심 성과: [Phase2] 게시판 목록 조회 API 성능 최적화

### 📌 Why: 무엇을 해결하고 싶었나요?

게시판의 핵심 기능인 '게시글 목록 조회' 기능 구현 후, 쿼리 로그를 분석하는 과정에서 숨겨진 성능 병목을 발견했습니다. 게시글을 조회하는 1개의 쿼리 이후, 각 게시글에 연결된 댓글이나 작성자 정보를 가져오기 위해 **게시글의 수(N)만큼 추가 쿼리가 발생하는 N+1 문제**였습니다.

이는 데이터가 수백, 수천 건으로 증가할수록 서버에 심각한 부하를 주어 **서비스 전체를 마비시킬 수 있는 잠재적인 장애 포인트**였습니다.

---

### 🛠️ What: 그래서 무엇을 만들었나요?

N+1 문제를 해결하기 위해 **Fetch Join**을 적용하여 연관된 엔티티를 단 한 번의 쿼리로 함께 조회하도록 JPQL을 개선했습니다. 

나아가, Fetch Join의 잠재적 단점을 보완할 더 나은 대안을 탐구하기 위해 **세미 조인(Semi-Join)과 스트림 API를 조합하는 방식**과 기존 방식의 성능을 **객관적인 데이터로 비교하는 테스트 환경**을 설계했습니다.

---

### 🔍 How: 이 목표를 어떻게 해결했나요?

#### 1. 문제 발견 및 Fetch Join을 통한 1차 해결

- `@SpringBootTest` 환경에서 API를 테스트하며 실행되는 쿼리 로그를 통해 N+1 문제를 명확히 인지했습니다.
- 가장 널리 알려진 해결책인 **Fetch Join**을 적용하여 즉시 로딩이 필요한 연관 관계의 엔티티를 함께 조회하도록 Repository 코드를 수정하여 1차적으로 문제를 해결했습니다.

#### 2. 이론에 기반한 심화 탐구 및 대안 가설 수립

Fetch Join이 야기할 수 있는 문제점을 학습했습니다:

- **카테시안 곱(Cartesian Product)**: 1:N 관계에서 게시글이 답변 개수만큼 중복 전송되어 네트워크 비용 증가
- **페이징 한계**: DB가 아닌 메모리에서 페이징이 처리되어 `setMaxResults`가 의도대로 작동하지 않음

이때, 기초 데이터베이스 이론을 공부하며 배웠던 세미 조인(Semi-Join)이 조인 연산의 비용을 크게 줄여준다는 사실을 떠올렸습니다.

**세미 조인의 핵심 원리**: 조인에 필요한 최소한의 키(ID) 정보만 먼저 추출하여 데이터 전송량을 줄이는 관계 대수 연산

이 이론적 지식을 바탕으로, **필요한 ID 목록만 먼저 조회하고(세미 조인 원리 응용), 조회된 독립적인 데이터들을 애플리케이션단에서 스트림 API로 조합하면 Fetch Join보다 효율적일 수 있다**는 새로운 가설을 수립했습니다.

**스트림 API를 선택한 이유:**

- **DB 레벨 최적화의 한계 보완**: 세미 조인 전략으로 3개의 독립적인 쿼리 결과를 받아오면, 이를 조합하는 과정이 필수적으로 필요합니다.
- **O(n) 시간 복잡도 보장**: `Collectors.toMap()`으로 답변 개수를 Map 구조로 변환하여 O(1) 조회가 가능하게 만들고, `stream().map()`으로 최종 DTO를 조립합니다. 전통적인 이중 반복문 방식은 O(n²)의 복잡도를 가지지만, 스트림 API와 Map을 활용하면 O(n)으로 개선됩니다.
- **선언적 코드**: 함수형 프로그래밍 패러다임을 통해 "무엇을 할 것인가"에 집중하여 코드 가독성과 유지보수성을 높였습니다.

#### 3. 객관적 검증을 위한 테스트 설계

두 방식의 성능을 정확히 비교하기 위해, 실제 프로덕션 환경을 시뮬레이션하는 테스트 인프라를 구축했습니다:

- Local MySQL 8.0 환경 구성 (Docker 대신 로컬 인스턴스 사용으로 I/O 오버헤드 제거)
- **10,000개 게시글, 100,000개 답변**의 대용량 더미 데이터 생성 (게시글당 평균 5~20개 답변)
- **Hibernate Statistics API**를 활용한 정밀한 성능 지표 수집 (쿼리 수, 엔티티 로드 수, 실행 시간)

### 💡 데이터 규모별 성능 분석

#### 핵심 인사이트

| 데이터셋 | Semi Join | Fetch Join | 성능 개선율 | Entity Load 비율 |
|---------|-----------|------------|------------|------------------|
| 1,000건 | 20ms | 683ms | 97.1% | 40 vs 14,277 (357배) |
| 5,000건 | 16ms | 1,430ms | 98.9% | 40 vs 68,125 (1,703배) |
| 10,000건 | 70ms | 6,506ms | 98.9% | 40 vs 136,518 (3,413배) |

**1. 스케일 효율성**
- Semi Join은 데이터 증가에도 안정적 성능 유지 (16-70ms)
- **이유**: 페이지네이션(20개 제한)으로 항상 동일한 엔티티(40개)만 로드

**2. Cartesian Product의 재앙**
- Fetch Join은 데이터가 10배 증가할 때 성능이 9.5배 악화 (683ms → 6,506ms)
- **이유**: 질문당 평균 10개 답변 → 10배 중복 전송 (14,277개 → 136,518개)

**3. 답변 수와의 상관관계**
- 답변이 많을수록 (평균 5-20개) Fetch Join의 Cartesian Product 문제가 극대화되어 Semi Join의 성능 우위가 더욱 명확해졌습니다.

**4. 예외 시나리오**
- 답변이 1-2개로 매우 적은 경우, Fetch Join의 단일 쿼리 장점(네트워크 왕복 1회)이 Semi Join의 3회 쿼리 비용을 상쇄할 수 있습니다 (추가 검증 필요)

### 📖 실무 적용 가이드 (When to Use Which)

각 쿼리 전략의 Trade-off를 기반으로 한 실무 의사결정 기준:

| 상황 | 권장 방식 | 이유 |
|------|----------|------|
| 1:N 관계에서 N이 많은 경우<br>(평균 5개 이상) | **Semi Join** | Cartesian Product 방지로<br>네트워크 비용 최소화 |
| 페이징이 필수인 API<br>(게시판, 목록 조회) | **Semi Join** | DB 레벨에서 정확한 페이징 보장 |
| N이 매우 적은 경우<br>(평균 1-2개) | **Fetch Join 고려** | 단일 쿼리로 네트워크 왕복 감소<br>(단, 검증 필요) |
| 프로덕션 환경 | **Lazy Loading 금지** | N+1 문제로 서비스 마비 위험 |

#### 의사결정 프로세스

1. 평균 연관 엔티티 수 확인 (5개 이상 → Semi Join)
2. 페이징 요구사항 확인 (필수 → Semi Join)
3. 성능 테스트로 최종 검증 (본 프로젝트처럼 Hibernate Statistics 활용)

## 🎤 Q&A

### Q: "Fetch Join이 더 나은 경우도 있지 않나요?"

**A**: 네, 1:N 관계에서 N이 1-2개로 매우 적을 때는 Fetch Join의 단일 쿼리 장점이 있을 수 있습니다. 하지만 본 테스트의 게시판 시나리오(평균 10개 답변)에서는 Cartesian Product 비용이 압도적이어서 Semi Join이 97-99% 빠릅니다.

### Q: "3개 쿼리 vs 1개 쿼리, 네트워크 레이턴시는?"

**A**: 로컬 MySQL 환경에서는 레이턴시가 1ms 미만이지만, 실제 프로덕션(원격 DB)에서 3회 왕복 비용(~15ms)이 발생합니다. 그러나 Fetch Join의 Cartesian Product로 인한 데이터 전송량(136,518 vs 40 엔티티)이 훨씬 큰 병목입니다. 테스트 결과(Semi 70ms vs Fetch 6,506ms)가 이를 증명합니다.

### Q: "왜 1K, 5K, 10K를 선택했나요?"

**A**: 스케일 증가에 따른 성능 추세를 관찰하기 위함입니다. 실제로 1K→10K(10배 증가) 시 Fetch Join은 9.5배 느려졌지만, Semi Join은 페이지네이션으로 3.5배만 느려져 스케일 효율성을 입증했습니다.

## 🎯 핵심 성과: [Phase 3] 동시 트래픽 환경의 병목 제거 및 Observability 구축

### 📌 Why: 무엇을 해결하고 싶었나요?

'단일 스레드에서 빠른 쿼리가 100명이 동시에 접속하는 실제 환경에서도 유효한가?'라는
의문을 검증하고자 했습니다. 특히 인덱스를 타지 않는 앞 와일드카드(LIKE "%kw") 검색과
값비싼 실시간 집계 연산이 동시 트래픽 상황에서 시스템을 어떻게 무너뜨리는지 k6로
측정하고 이를 개선했습니다.

### 🔍 How: 이 목표를 어떻게 해결했나요?

1. Full-Scan 제거 (Index Optimization): Covering Index: `ORDER BY + LIMIT` 쿼리의 filesort를 제거하고, 인덱스만으로 응답을 완결하여 Row Lookup 비용을 제거했습니다.
   
2. FULLTEXT Index (ngram): 앞 와일드카드 검색을 `MATCH...AGAINST` 방식으로 교체하여 MySQL의 역색인(Inverted Index)을 활성화했습니다.
   
3. 집계 부하의 완전 분리 (Architectural Decoupling): 매 요청마다 수행되던 주간 랭킹 집계를 **Spring Scheduled 배치로 분리**했습니다. 사전 계산된 결과를 전용 테이블(TRENDING_QUESTION)에 저장함으로써 요청 경로(Request Path)에서
무거운 연산을 완전히 제거했습니다.

4. 병목 가시화 (Prometheus & Grafana): 단순한 성공 여부를 넘어 커넥션 풀 상태,
쿼리 응답 시간 등을 시각화하여 데이터 기반의 디버깅 환경을 구축했습니다.

> ℹ️ 시나리오 A(사용자 대면 검색)와 시나리오 B(백그라운드 집계)는 서로 다른 엔드포인트이며, 응답 지연 허용 기준(SLO)도 각각 3초, 500ms로 다르게 설정했습니다. 아래 결과는 두 시나리오를 독립적으로 측정한 것입니다.

### 📊 Result: 어떤 결과를 얻었나요? (100 VU 동시 접속 환경)

#### 1. 시나리오 A: 검색 성능 최적화 (Index Tuning)

풀스캔 발생으로 사실상 서비스 불가능 수준이었던 검색 성능을 인덱스 고도화를 통해
정상화했습니다. 특히, 앞의 How에서 첫번째 방법인 Covering Index와 2번째 방법인
FULLTEXT 인덱스를 혼합해서 사용함으로써 다음과 같은 개선된 수치를 얻을 수
있었습니다.

##### Before/After 성능 분석 (기준: 목표 응답시간 3s)

| 지표 | Before (LIKE 풀스캔) | Phase 3 (인덱스 추가) | Phase 4 (OR→UNION) |

> Phase 4에서 TPS가 낮아 보이는 것은 성능 저하가 아니라, 이번에야 모든 요청이 실제로 검색을 수행했기 때문입니다.

#### 1-1. Phase 4: 인덱스를 만들어놓고 쓰지 못하고 있었습니다

Phase 3을 마칠 때 저는 "인덱스 최적화만으로 에러율이 51.58%까지밖에 안 내려간 것은
쿼리가 아니라 **HikariCP 커넥션 풀 포화** 같은 인프라 병목 때문"이라고 추정했습니다.
이 가설을 검증하려고 풀 사이즈를 20→40→80으로 늘려봤지만 에러율은 50~52%에서 꿈쩍하지 않았습니다.

가설이 틀렸다는 것까지는 확인했으나, 왜 틀렸는지는 애플리케이션 로그를 열어보고 나서야 알았습니다.

**원인 1 — 네이티브 쿼리의 ORDER BY 중복 (에러율 50%의 정체)**

```
SQLSyntaxErrorException: Unknown column 'q.createDate' in 'order clause'
... ORDER BY q.CREATE_DATE DESC, q.createDate desc limit ?
```

FULLTEXT 검색용 네이티브 쿼리는 `ORDER BY q.CREATE_DATE DESC`를 이미 포함하는데,
페이지네이션을 위해 넘긴 `Pageable`의 `Sort(createDate)`가 뒤에 한 번 더 붙었습니다.
네이티브 쿼리에는 프로퍼티명→컬럼명 변환이 없어 `q.createDate`가 그대로 나갔고 MySQL이 거절했습니다.
Sort는 JPQL 경로만 있던 시절에 추가한 코드였는데, Phase 3에서 네이티브 쿼리를 도입하며
같은 `Pageable`을 재사용한 것이 원인이었습니다. 시나리오의 키워드 검색 가중치가 정확히 50이라
에러율이 풀 사이즈와 무관하게 50%에 고정돼 있었습니다.

**원인 2 — OR 조건이 FULLTEXT 인덱스를 무력화 (진짜 병목)**

버그를 고치고 다시 측정하자 이번엔 에러율이 78.65%, P95가 36초로 치솟았습니다.
그동안 절반이 즉시 실패하며 숨겨져 있던 실제 부하가 처음으로 드러난 것입니다.
`performance_schema`로 쿼리별 시간을 보니 **count 쿼리 하나가 전체 DB 시간의 92%** 였고,
평균 8초에 27만 행을 검사하고 있었습니다.

```sql
WHERE MATCH(q.SUBJECT, q.CONTENT) AGAINST (:kw IN BOOLEAN MODE)
   OR u1.USERNAME LIKE %:kw%   -- ← 앞 와일드카드라 인덱스 사용 불가
```

`OR`의 한 항이 인덱스를 타지 못하면 MySQL은 어차피 전체를 봐야 한다고 판단해
**같은 WHERE 절의 `MATCH AGAINST`까지 FULLTEXT 인덱스를 버립니다**(`EXPLAIN`에서 `type=ALL`, `possible_keys=NULL`).
여기에 `LEFT JOIN ANSWER`가 질문 1만 건을 12만 5천 행으로 부풀렸습니다.
**Phase 3에서 만든 `ft_idx_question_search`와 `idx_question_covering`은 이 시점까지 단 한 번도 사용되지 않았습니다.**

조건 3개를 `OR` 대신 `UNION`으로 분리해 각 항이 자기 인덱스를 타게 하자
(결과 집합은 동일 — 중복은 UNION이 제거) count 쿼리가 8090ms/271,373행에서
**59.7ms/884행으로 135배** 빨라졌고, threshold 2개를 처음으로 모두 통과했습니다.

| 쿼리 | 개선 전 | 개선 후 |
|---|---|---|
| count 쿼리 | 8090ms · 271,373행 · `type=ALL` | 59.7ms · 884행 · `Full-text index search` |
| 목록 쿼리 | 256ms | 107ms · `idx_question_covering` 사용 |

**배운 점**: 인덱스를 만들었다는 사실과 쿼리가 그 인덱스를 쓴다는 사실은 별개입니다.
`EXPLAIN`으로 실제 사용 여부를 확인하지 않은 채 "인덱스를 추가했으니 개선됐을 것"이라고 가정했고,
남은 에러를 인프라 탓으로 돌렸습니다. 부하 테스트 수치만 보고 원인을 추정하는 대신
애플리케이션 로그와 `performance_schema`를 먼저 열어봤다면 훨씬 일찍 찾았을 문제였습니다.

현재 병목은 N+1로 이동했습니다(답변 조회 62,796회 + 작성자 조회 52,519회 = 전체 DB 시간의 34%).
상세 측정 데이터는 `results/summary_metrics_union.txt`에 있습니다.

#### 2. 시나리오 B: 집계 부하 분리 (Batch Processing)

실시간 집계 로직을 요청 경로에서 완전히 제거함으로써, 랭킹 API가 메인 검색 트래픽과 무관한 별도의 안정적인 성능 특성을 갖도록 만들었습니다. 앞의 How의 3번째 방법인 Spring Scheduled 배치로 매 요청마다 수행되던
주간 랭킹 집계를 분리함으로써 다음과 같은 개선된 수치를 얻을 수 있었습니다.

##### 최종 성능 분석 (기준: 목표 응답시간 500ms)

| 지표 | 결과 |
|---------|-----------|
| P95 응답 시간 | 83.98ms |
| 목표 응답시간 초과율 | 0.00% |
| HTTP 실패율 | 0.00% |

100 VU의 극한 상황에서도 랭킹 API는 목표 응답시간(500ms) 초과율 0.00%로 threshold를 통과시켜, 장애 없는 서비스 환경을 구축했습니다.

> 시나리오 A와 B는 검색과 집계라는 서로 다른 책임을 가진 엔드포인트입니다. 따라서 두 시나리오의 수치를 하나의 표로 직접 비교하지 않고, 각각 자신의 SLO(3s / 500ms) 대비 얼마나 안정화되었는지로 평가했습니다.

### 🏆 결론 및 배운 점

1. 성장의 궤적: [Phase 1]으로 단순 기능 구현에서 시작해, [Phase 2]의 쿼리 튜닝을 거쳐, 최종적인 [Phase 3]의 시스템 레벨의 부하 테스트 및 모니터링까지 백엔드 엔지니어로서의
가치 사슬을 확장했습니다.

2. 데이터 중심 사고: 막연한 예측이 아닌 k6 부하 테스트와 Grafana 지표를 통해 병목을
특정하고 개선 수치를 정량적으로 증명하는 습관을 길렀습니다.

3. 트레이드오프의 이해: 실시간성(Real-time)과 안정성(Stability) 사이에서 배치 처리를 선택하는 등, 비즈니스 상황에 맞는 기술적 의사결정 역량을 내재화했습니다.
