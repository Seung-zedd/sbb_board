# P95 무릎(knee) 탐색 결과 — 2026-08-09

측정 대상: baseline 빌드(`8678b20`, UNION 수정 포함 / N+1 개선 **미포함**)
시나리오: `load-test/scenario-knee.js` (constant-arrival-rate, open model)
구성: 워밍업 5 req/s 20초 → 본 측정 2분. 트래픽 분포는 `scenario-a.js`와 동일(빈 검색 50% / 키워드 검색 50%).
환경: Prometheus·Grafana 정지, Gradle 데몬 정지, MySQL 컨테이너만 기동.

## 결론

| 항목 | 값 |
|---|---|
| 무릎(포화 시작) | **25~28 req/s 사이** |
| 최대 처리량 | 약 **27~29 req/s** (그 이상 요청하면 오히려 감소) |
| A/B 권장 도착률 | **20 req/s** (무릎의 약 0.7배, 드롭 0건, P95 187ms) |

rate 28 이상에서는 실제 처리량이 목표를 못 따라가고(19.1 / 26.6 / 29.1 req/s),
드롭률이 11~32%로 뛴다. rate 30에서 목표를 30으로 올려도 처리량은 오히려
26.6 → 22.3 → 15.1로 떨어지는 실행이 나왔다. 전형적인 congestive collapse.

## 측정 도중 밝혀낸 것 — 8/8 편차의 정체

8/8에 "같은 코드가 15.7~40.3 TPS를 오갔다"고 기록한 잡음의 원인을 특정했다.

**호스트 간섭이 수십 초~2분 단위 에피소드로 발생한다.**

근거:

1. 동일 코드·동일 도착률(10 req/s) 4회에서 P95가 5862 / 5166 / 3502 / 633 ms.
2. 시계열을 10초 버킷으로 쪼개니 부하는 일정한데 **25초~85초 구간에서만**
   중앙값이 211ms → 2918ms로 14배 뛰었다가 160ms로 복귀했다
   (`results/knee_r10_ts.csv`). 포화라면 높은 상태가 유지되지 튀었다 돌아오지 않는다.
3. 유휴 시 단일 요청은 99~124ms인데, 평균 동시성 1 수준의 부하에서 P95가 5초까지 갔다.

### 기각된 원인

| 가설 | 근거 |
|---|---|
| JVM GC | jstat 176초 관측, 총 GC 0.345초(0.2%), Full GC 0건 |
| 스케줄 배치 | `TrendingQuestionService`는 `fixedRate = 3_600_000`(1시간), 세션 중 1회만 실행 |
| JIT/버퍼풀 콜드스타트 | 데워진 상태에서 재측정해도 P95 5166ms 재현 |
| 서버 오류 | 전 구간 `status != 200` 0.00% |

### 이번에 정정한 오판

rate 15와 20의 1회차는 P50 2751ms / 3056ms가 나와 "무릎이 15에 있다"고 판단했으나,
재측정에서 63ms / 83ms, 드롭 0건이 나왔다. **간섭이 2분 런 전체를 덮을 수 있다.**
따라서 런 내부 정상성(버킷 간 균질성)만으로는 오염을 잡아낼 수 없고,
같은 조건 반복 측정이 필수다. 실제로 rate 30은 3회 모두 포화가 재현되어
진짜 포화로 확정할 수 있었다.
