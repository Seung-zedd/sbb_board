## 어제(8/7) 실험과 달라진 조건 3가지
1. QuestionService.getList의 ORDER BY 중복 버그 수정 (커밋 560bb0e)
   -> 어제는 키워드 검색 경로(트래픽의 50%)가 MySQL 1054로 100% 즉시 500이었다.
2. p6spy 쿼리 로깅 비활성화 (loadtest/performance 프로파일)
   -> 매 쿼리 파일 I/O 제거. 앱 로그 571MB -> 576KB.
3. DummyDataGenerator 개선 + 데이터 재생성
   -> scenario-a.js의 키워드 7종을 15/12/9/7/5/3/1% 비율로 주입.
      어제는 6종이 0건 매칭, 1종("테스트")이 전건 매칭이었다.
      건수는 동일 수준 유지 (Q 10000 / A 125692 / U 1000).

## 해석

버그는 확실히 제거됐다 (q.createDate 에러 0건, 키워드 검색 4종 모두 HTTP 200 확인).

그런데 수치는 전 항목이 나빠졌다. 이는 성능이 나빠진 것이 아니라
어제 측정이 부하를 제대로 걸지 못하고 있었다는 뜻이다:

- 어제는 트래픽의 50%가 SQL 문법 오류로 즉시 예외 처리됐다. 예외 경로는 커넥션을
  잡자마자 놓아버리므로 풀에 걸리는 실질 압박이 실제의 절반 이하였다.
- 어제 "성공"으로 집계된 나머지 50%(kw='' 전체 목록)도 결과가 가벼운 쪽이었다.
- 이번에는 모든 요청이 실제로 검색을 수행한다. 그 결과 커넥션 점유 시간(usage)이
  290ms -> 5382ms로 약 18배가 됐고, 풀 20개가 전부 포화되어 대기 41~45건,
  connection timeout 14건이 발생했다.

>>> 어제의 결론("HikariCP 풀 포화 가설 반증, 병목은 DB 실행시간")은
>>> 잘못된 실험 조건에서 나온 것이므로 폐기해야 한다.
>>> results/summary_metrics.txt의 VERDICT 절 전체가 여기에 해당한다.

다만 "풀 가설이 맞았다"로 뒤집는 것도 성급하다. 산술이 그것을 지지하지 않는다:
  이론 처리량 = pool_size / usage = 20 / 5.38s = 3.7 TPS
  실측 TPS    = 3.1
거의 일치한다. 즉 풀 포화는 원인이 아니라 usage(=쿼리 실행 시간)가 5초대라는
사실의 결과다. 풀을 늘려도 동시 쿼리 수만 늘어 usage가 함께 늘어날 가능성이 높다
(어제 pool 40/80 실험에서 관측된 usage 증가 경향과 같은 방향).

## 다음 조사 대상 (우선순위 순)

1. N+1 — QuestionListItemDto.from이 question.getAnswerList().size()를 호출한다.
   목록 10건 조회마다 답변 조회 쿼리가 10회 추가된다. 답변 12만 건 기준으로
   usage 5초의 주요 후보. countQuery로 대체하거나 @BatchSize/fetch join 검토.
2. 키워드 검색 쿼리의 LEFT JOIN ANSWER + DISTINCT — 질문 1만 x 답변 평균 12.5개의
   카티전 곱을 만든 뒤 DISTINCT로 걷어낸다. 현재 쿼리는 answer.CONTENT를 검색
   조건으로 쓰지도 않으므로 이 조인이 필요한지부터 재검토.
3. kw='' 경로도 단독 8초가 나왔다(워밍업 포함). 검색 유무와 무관한 공통 병목이
   있다는 뜻이므로 1번(N+1)을 먼저 확인하는 근거가 된다.
