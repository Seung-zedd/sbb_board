# 키워드 검색 STEP 1: IN (서브쿼리) → JOIN (파생 테이블) 실측

측정일 2026-08-09 · 재현 `bash load-test/bench-kw-join.sh 7` · 실행계획 `load-test/explain-kw-join.sql`

DB 단독 측정입니다. 앱은 전부 정지, MySQL 컨테이너만 기동한 상태에서 `SET profiling=1` +
`SHOW PROFILES`로 statement별 duration을 받았습니다. 7회 반복 중 **최소값**을 참값으로 봅니다
(이 호스트는 지연을 늘리는 방향으로만 작용하는 간섭 에피소드를 일으킵니다 —
`NEXT_STEPS_2026-08-09.md` "측정할 때 반드시 지킬 것" 2항).

## 무엇을 바꿨나

```sql
-- A. 이전
SELECT q.ID FROM QUESTION q WHERE q.ID IN (<UNION 3항>) ORDER BY q.CREATE_DATE DESC

-- B. 이후
SELECT q.ID FROM QUESTION q JOIN (<UNION 3항>) t ON t.ID = q.ID ORDER BY q.CREATE_DATE DESC
```

countQuery는 원래부터 파생 테이블 형태(`SELECT COUNT(*) FROM (<UNION 3항>) t`)라 손대지 않았습니다.

## 실행계획이 말하는 것

| | A: IN | B: JOIN |
|---|---|---|
| UNION 평가 | `DEPENDENT SUBQUERY` / `DEPENDENT UNION` — 바깥 q의 매 행마다 재평가 | `DERIVED` — 1회 실체화 |
| MATCH AGAINST | `eq_ref PRIMARY (func)` — **FULLTEXT 인덱스를 못 탐** | `fulltext ft_idx_question_search` |
| 파생 테이블 조인 | — | `eq_ref <auto_distinct_key>` |
| 결과 집합 (kw=자바) | 1,475건 | **1,475건 (동일)** |

## A의 비용은 매칭 건수에 반비례한다

이게 이번 측정의 핵심입니다. `ORDER BY CREATE_DATE DESC LIMIT 10`이 10건을 채울 때까지
q를 훑는데, 매 행마다 UNION 3항을 다시 평가합니다. **매칭이 드물수록 더 많이 훑습니다.**

|---|---|---|---|---|---|---|---|
| 자바 | 1,475 | 4.80 | 6.47 | 6.29 | 11.09 | 12.76 | +15% |
| 스프링 | 1,152 | 11.76 | 12.36 | 12.95 | 24.71 | 25.31 | +2% |
| JPA | 891 | 17.71 | 12.88 | 12.14 | 29.85 | 25.02 | −16% |
| 쿼리 | 643 | 16.77 | 4.56 | 4.32 | 21.09 | 8.88 | −58% |

## 경계 조건

| kw | 성격 | A (목록) | B (목록) | C (count) | A+C | B+C |
|---|---|---|---|---|---|---|
| 질문 | FT 0건. 사용자가 실제로 칠 법한 흔한 단어 | 505.64 | 5.39 | 1.33 | 506.97 | **6.72 (−99%)** |
| zzzznotfound | 매칭 0건 | 437.93 | 4.10 | 1.02 | 438.95 | **5.12 (−99%)** |
| user1 | USERNAME LIKE가 111명 매칭 → 파생 테이블 비대 | 1.50 | 34.86 | 35.18 | **36.68** | 70.04 (+91%) |

**A의 진짜 문제는 여기입니다.** 매칭 0건 검색어 하나가 500ms를 먹습니다.
DB 시간의 84%가 키워드 검색이었던 이유이기도 합니다.

**B의 정직한 약점도 여기 있습니다.** `user1`처럼 작성자명이 대량 매칭되는 키워드에서는
파생 테이블 실체화 비용이 그대로 드러나 A보다 2배 느립니다. 다만
그 조건에서는 count 쿼리(C)가 이미 35ms를 쓰고 있어 **A를 써도 36.7ms**입니다.
피할 수 있는 비용이 아니라 UNION 구조 자체의 비용입니다.

채택합니다. 근거는 셋입니다.

1. 결과 집합이 동일합니다. 키워드 5종 × 2페이지에서 id 목록(순서 포함)과 전체 건수가
   IN 버전과 일치합니다 — `QuestionSearchRegressionTest.findQuestionIds_matchesLegacyEntityQuery`.
2. 실측 가중 평균 −32%, 최악 케이스 −99%.
3. 손해 보는 구간(자바 +1.7ms)이 절대값으로 작고, 그 대가로 500ms 꼬리가 사라집니다.

## 남은 것 — 다음 후보는 count 쿼리다

B 전환 후 목록 쿼리 비용이 count 쿼리와 거의 같아졌습니다(`B ≈ C`).
둘이 같은 파생 테이블을 각각 한 번씩 실체화하기 때문입니다. 즉 **지금은 같은 일을 두 번 합니다.**

`스프링`(B 12.36 / C 12.95), `JPA`(12.88 / 12.14), `user1`(34.86 / 35.18)에서
count가 전체의 절반입니다. 여기를 줄이면 남은 절반이 열립니다. 다만 UNION의 중복 제거가
전체 실체화를 요구하므로 쿼리 재작성만으로는 어렵고, 구조 변경(카운트 캐싱, 근사 카운트,
무한 스크롤 전환 등)이 필요합니다. 별건으로 둡니다.
