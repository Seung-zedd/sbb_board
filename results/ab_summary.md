# N+1 제거 A/B 측정 결과 — 2026-08-09

8/8에 판정 불가로 남겼던 질문에 답이 나왔다.

**질문**: 질문 목록 N+1 제거(세미조인 3단계 전환)가 종단 응답시간을 실제로 줄이는가.
**답**: 줄인다. 쌍별 비교 5회에서 perf가 94.9~97.8%의 쌍에서 빨랐다.

## 비교 대상

| | 커밋 | 포트 |
|---|---|---|
| baseline | `8678b20` (UNION 수정 포함, N+1 **미개선**) | 8080 |
| perf | `8a56eca` (N+1 세미조인 3단계 전환) | 8081 |

사전 검증: 8종 쿼리(빈 검색 + 키워드 7종)에 대해 두 빌드의 HTTP 응답이
**바이트 단위로 동일**함을 md5로 확인했다. 성능 차이는 동작 변경 때문이 아니다.

## 왜 순차 측정을 버리고 쌍 측정으로 갔나

8/9 무릎 탐색에서 이 호스트는 수십 초~2분짜리 간섭 에피소드를 일으킨다는 것을 확인했다
(`knee_summary.md`). 동일 코드·동일 도착률 4회에서 P95가 5862 / 5166 / 3502 / 633 ms였고,
간섭이 2분 런 전체를 덮은 경우도 있었다. 이 조건에서 "baseline 런"과 "perf 런"을 따로 재면
두 런이 서로 다른 간섭을 맞아 결론이 통째로 뒤집힌다. 8/8에 7회를 재고도 판정하지 못한 이유다.

그래서 두 빌드를 동시에 띄우고 **한 반복 안에서 둘 다** 때렸다. 통제 세 가지:

1. **쿼리 동일** — 한 쌍의 두 요청은 완전히 같은 URL
2. **순서 교대** — 반복마다 먼저 때리는 쪽을 뒤집음 (뒤 요청이 버퍼 풀 덕을 보는 편향 제거)
3. **쿼리 시퀀스 고정** — 고정 시드로 섞은 배열을 반복 인덱스로 참조 (런 간 재현 가능)

## 설계 검증 — 널 대조

양쪽 URL을 **같은 앱(8080)**으로 겨눈 대조 실험:

| 지표 | 값 | 기대값 |
|---|---|---|
| perf 쪽이 빠른 쌍 비율 | **48.6%** | 50% |
| P50 상대 차이 | +0.7% | 0% |
| 먼저 / 나중 맞은 쪽 P50 | 11558ms / 11588ms | 동일 |

이 대조 런은 심하게 오염된 상태였다(P50 11.5초). **그런데도 "차이 없음"을 정확히 보고했다.**
순차 측정이 무너지는 조건에서 이 설계는 버틴다.

### 채택할 수치

**깨끗한 런(run2)의 값을 정식 결과로 삼는다.**

| | baseline | perf | 변화 |
|---|---:|---:|---:|
| P50 | 93ms | 54ms | **-42%** |
| P95 | 206ms | 138ms | **-33%** |
| P99 | 457ms | 287ms | -37% |

오염된 런의 -85~-90%는 과장이다. 시스템이 큐잉 상태에 들어가면 느린 쪽이
불균형하게 더 느려지기 때문이다. 다만 방향과 승률은 오염 여부와 무관하게 일정했다.

### 순서 효과 점검

먼저 맞은 쪽 73ms / 나중에 맞은 쪽 75ms (run2). 차이 2ms.
순서 교대가 캐시 선행 효과를 상쇄하고 있다.

## 결론

N+1 제거 커밋을 **유지한다**.

- 쿼리 레벨: 목록 1페이지 21쿼리 → 4쿼리, 답변 엔티티 로드 0
- 종단 응답시간: P50 -42%, P95 -33% (동시 쌍 측정, 널 대조로 설계 검증)
- 동작: 응답 바이트 동일
- 비용: Service에 조립 로직이 늘어 코드가 복잡해짐 — 위 이득으로 정당화된다고 본다
