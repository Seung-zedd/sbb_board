[결론 요약]

1. 8/8 기록(P95 2727ms / 에러율 1.54%)은 오늘 환경에서 재현되지 않는다.
   8/8과 한 글자도 다르지 않은 코드가 오늘 P95 4292ms / 에러율 25.84%로 측정됐다.
   => 8/8 수치를 오늘의 기준선으로 쓸 수 없다. 날짜를 건너뛴 비교는 무효.

2. 오늘 같은 조건에서 비교하면 N+1 제거는 처리량을 +13.5% 올렸고
   에러율은 동일하며 P95는 악화됐다.

3. VU 100 부하에서 DB 시간의 84%는 키워드 검색 쿼리다. N+1이 있던 자리는 6%.
   => N+1을 완전히 없애도 P95는 구조적으로 내려가지 않는다.

[검증된 것 / 반증된 것]

반증 1: "SELECT q.* -> SELECT q.ID 변경이 실행계획을 망가뜨렸다"
        => EXPLAIN 결과 두 버전의 계획이 완전히 동일. (load-test/explain-step1.sql)

반증 2: "데이터/인덱스 상태가 8/8과 달라졌다"
        => 키워드 매칭 건수가 8/8과 일치(자바 1475건). (load-test/kw-match-counts.sql)

부분 확인: 버퍼 풀 콜드 스타트는 실재하는 요인이다(P95 7094 -> 5782ms).
           다만 워밍 후에도 8/8 수치에 못 미쳐 단독 원인은 아니다.

기능 동등성: 신구 UNION 쿼리가 키워드 5종에서 전체 건수와 1페이지 id 순서까지
             동일함을 테스트로 확인(QuestionSearchRegressionTest).


[다음 타깃 — Phase 3 VU 100 기준]

EXPLAIN이 보여준 84% 구간의 정체:

    DEPENDENT SUBQUERY / DEPENDENT UNION, rows_examined 평균 5,993

UNION 서브쿼리가 상관 서브쿼리로 실행되어 바깥 행마다 재평가된다.
바깥 q는 idx_question_covering을 CREATE_DATE 순으로 스캔하며 10건을 채울 때까지
각 행에서 서브쿼리를 다시 돌린다.

개선 방향: IN (서브쿼리) -> JOIN (파생 테이블)
    SELECT q.* FROM QUESTION q
    JOIN (SELECT ... UNION SELECT ... UNION SELECT ...) t ON t.ID = q.ID
    ORDER BY q.CREATE_DATE DESC
파생 테이블은 한 번만 평가되므로 DEPENDENT가 사라진다. 미검증.
